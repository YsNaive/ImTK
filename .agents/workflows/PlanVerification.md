# 實作計畫完備性驗證 (Plan Verification)

此 Workflow 的目的是在 AI 或開發者開始執行任何實作計畫 (Implementation Plan) 之前，嚴格審查該計畫是否符合 ImTK 的架構規範、效能要求與防呆機制，避免破壞現有生態或產生技術債。

## 🎯 啟動條件
當使用者輸入 `/PlanVerification`、要求驗證一份計畫，或在準備執行重大架構變更的 `implementation_plan.md` 之前，請主動執行此 Workflow。

## 📋 驗證步驟 (Verification Steps)

請作為一名嚴謹的「ImTK 架構審查員」，**依序**執行以下步驟，並在最終回答中清楚呈現您的審查結果：

### 步驟 1：情資蒐集與脈絡理解 (Context Gathering)
1. **閱讀最高指導原則**：重新檢視 `AGENTS.md` 中的核心開發規範 (例如 1.4 指標記憶體安全、1.5 Property Over Field 等)。
2. **定位相關子模組**：分析目前的實作計畫牽涉到哪些子系統 (例如 `Core`, `UI`, `Database` 等)。
3. **查閱模組速查表**：主動查閱牽涉到的子目錄中的 `README.md` (Cheat Sheet) 或架構文件，確保您完全理解該模組當前的架構事實與防呆限制。

### 步驟 2：架構與規範審查 (Architecture & Rule Check)
請針對計畫內容，回答以下關鍵問題。若有疑慮，必須明確指出：
* **記憶體安全 (Zero-GC)**：計畫中是否包含高頻的字串相加？呼叫 ImGui 底層時是否有違規使用 `fixed` 語句？是否正確使用了 `NativeUtf8Buffer`？
* **生命週期與事件 (Lifecycle & Events)**：若有註冊全域事件，是否有確實規劃在 `OnDisable` 階段解除綁定？如果是 UI 元素的改動，是否有遵守「嚴禁在 GuiRender 階段直接修改視覺樹結構」的鐵則 (需使用延遲派發 `ScheduleDeferred` 等機制)？
* **模組建構限制**：若計畫中包含新增 `ImTKModule`，是否有確保它只有唯一且非公開的無參數建構函式？

### 步驟 3：邊界條件與副作用盤點 (Edge Cases & Side Effects)
* **Fallback 與防呆**：若涉及資源讀寫，檔案不存在或反序列化失敗時的行為是什麼？
* **相依性衝擊**：此改動是否會打破現有其他模組的隱含假設？(例如修改排版引擎屬性是否會讓現有的 Drawer 或 Window 佈局跑掉？)

### 步驟 4：產出審查報告與「靈魂拷問」 (Report & Grill)
完成上述檢查後，請產出最終的審查報告。
1. **指出漏洞**：若發現計畫有遺漏或違反規範之處，請使用 GitHub Alert 語法 (例如 `> [!WARNING]`, `> [!CAUTION]`) 強烈提醒使用者。
2. **提出修改建議**：針對漏洞給出符合 ImTK 規範的具體修正方案。
3. **靈魂拷問 (Grill)**：若計畫中有模糊不清、未明確定義邊界條件的設計決策，列出 1~3 個尖銳但具有建設性的問題，要求使用者在開始寫 code 之前必須先釐清。

---

> [!IMPORTANT]
> **給 AI Agent 的最高指示**：寧可嚴苛地指出計畫缺陷並退回，也絕不放行任何帶有架構隱患、違反零分配 (Zero-GC) 或是破壞生命週期的程式碼進入執行階段。
