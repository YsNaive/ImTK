# ImTK 專案文檔架構規範 (Documentation Specifications)

為了確保專案技術文檔的一致性、易讀性以及「快速查找」的實用性，所有參與開發的成員（包含 AI Agent）在撰寫與維護 `docs/` 目錄下的文件時，必須嚴格遵守以下規範。

---

## 1. 模組入口定義 (Entry Point)

*   **唯一入口**：每一個獨立的子模組資料夾（例如 `docs/Event/`, `docs/UI/Element/`），**必須且只能**透過 `README.md` 作為唯一入口。任何開發者想了解某個模組，皆從該目錄的 README 開始。

## 2. `README.md` (總表) 的職責限制

`README.md` 的核心定位是該模組的「**速查表 (Cheat Sheet)** 與 **目錄索引**」。

*   **內容限制與格式**：
    1.  **模組簡介**：限制在幾句話內說明該模組解決了什麼問題、提供了什麼功能。
    2.  **API 速查 (Quick Reference)**：將該模組對外公開的可用類別、事件、主要函式進行條列。只需寫出名稱與一行簡短用途。
    3.  **子文件索引**：列出該模組下其他深入探討架構的 `*.md` 技術文件連結與簡要說明。
*   **禁忌**：嚴禁在 README 內寫大篇幅的底層運作機制、歷史沿革或複雜的架構圖。這些內容應移至獨立的技術文件中。

## 3. 技術架構文件 (`*.md`) 的職責限制

除了 README 以外的 `.md` 檔案（例如 `EventBus.md`），核心定位是探討「**深度架構與設計決策**」。

*   **內容限制與格式**：
    1.  **專注於機制**：解釋「為什麼這樣設計 (Why)」與「底層機制如何運作 (How)」。
    2.  **視覺化輔助**：鼓勵使用流程圖 (如 Mermaid) 或概念架構圖來輔助說明。
*   **禁忌**：避免在這些文件內大量重複列舉 API 清單或完整的類別成員，以免因後續程式碼重構而導致文檔脫節。

## 4. 程式碼溯源與連結 (Traceability)

為了確保「快速查找」的實用性並維持文檔的有效性：

*   **強制使用 Markdown 連結**：在 `README.md` 中的「API 速查清單」，**必須使用相對路徑的 Markdown 連結，直接指向實際的程式碼檔案位置**。
    *   *範例*：`[OnFontChangedEvent](../../ImTK/Event/OnFontChangedEvent.cs)`
*   如此一來，開發者無論是在 IDE 或 GitHub 介面上閱讀文檔，都能透過點擊直達原始碼進行查閱。

## 5. 零歷史包袱 (Factual Rule)

此規則與 `AGENTS.md` 的最高指導原則一致：

*   **只記錄當下事實**：所有的技術文件與 README **只紀錄「當下最新」的架構事實與運作方式**。
*   **禁忌**：絕不在技術文件內寫入類似「我們在 xxx 時候移除了 yyy」、「原先的設計是...後來改為...」或任何類似 Changelog 的歷史修改日誌。歷史追蹤請交給 Git 與 `CHANGELOG.md`。
