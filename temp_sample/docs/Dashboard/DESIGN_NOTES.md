# Dashboard 設計考量與工程妥協 (Design Notes)

本文件記錄了 Dashboard 子系統在設計與實作過程中，為克服物理與硬體限制所作的關鍵決策。未來開發者在維護此模組時，請務必理解這些前提，避免因「優化」而破壞了系統的健壯性。

## 1. 8Hz 刷新頻率與效能保護

**設計選擇**：底層 Dispatch Loop 以 8Hz 的頻率向序列埠發送更新，而不是與機器人主迴圈 (通常 100Hz+) 同步。
**原因**：
* VEXnet 無線通訊的物理極限即為 8hz，每個封包 200 bytes

## 2. 150 Bytes 實體傳輸限制與雙模式策略

**設計選擇**：單次傳輸 (Physical Transmission) 的大小被嚴格限制在 150 bytes 以內（預留 Header/Checksum 等後，最大 Payload 為 147 bytes）。
**原因**：這是為了適應 VEXnet 序列通訊在緩衝區溢出與延遲上的物理極限。若不分塊發送巨量數據，將導致嚴重的封包遺失。

**妥協與解決方案 (雙模式發送策略)**：
* **小封包聚合模式**：將多個小數值 (如 Float, Int32) 塞入同一個小於 150 bytes 的封包內，絕不切塊，確保即時性。
* **巨型封包切塊模式**：為了傳輸如 Odometry 的龐大路徑陣列，採用 `0xFF` 長度擴充標記建立巨型邏輯封包，並允許底層無情切碎，交由 C# 端以 Ring Buffer 重組。這避免了在應用層實作複雜的 Chunking。

## 3. 捨棄 JSON，採用自定義二進位序列化

**設計選擇**：沒有使用通用的序列化格式 (如 JSON)，而是自訂了基於 Type ID 的二進位壓縮。
**原因**：
* VEX 腦 (Brain) 的運算資源寶貴，解析 JSON 會消耗過多 CPU 週期。
* JSON 會傳輸大量的鍵名字串 (`"Speed": 100`)，在 150 bytes 的傳輸極限下極度浪費頻寬。
* **妥協作法**：採用「Entity ID」代理模式。第一次建立時傳送長字串並綁定一個 ID (0~255)，之後所有的更新皆只傳送該 ID，這將每次狀態更新的負擔壓縮至極致（如 Float 只需幾個 byte）。

## 4. 浮點數 (Float) 序列化特化

**設計選擇**：將 Float 乘上 100 後轉為 Int32 進行變長壓縮傳輸。
**原因**：這是一個經典的頻寬妥協。通常競賽機器的遙測數據不需要到非常精確的小數位，保留兩位小數 (x100) 即可大幅縮減浮點數標準 4 bytes 的佔用。

## 5. 無 ARQ 機制與 C# 端的 Fetch 重傳

**設計選擇**：VEX 端發送資料後「不等待 C# 端確認 (ACK)」，也沒有歷史佇列可供補發。
**原因**：為避免耗費 VEX 腦寶貴的記憶體去維護通訊狀態機，VEX 端被設計為「無腦廣播」最新狀態。
**補償機制**：如果因為無線電干擾導致封包遺失（例如 C# 端沒收到 `Create Entity`），**責任完全在 C# 接收端**。C# 端會發送 `Fetch Entity` (0x07) 主動要求 VEX 端重傳特定的變數建構資料。
